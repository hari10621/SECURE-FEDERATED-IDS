CORE PROJECT GOAL

Develop a genuine AI-powered Federated Intrusion Detection System
(F-IDS) for Software-Defined Networking (SDN).

Multiple clients must train local GRU models using their own
network-traffic datasets. They collaboratively create a global model
through federated learning without sharing raw training datasets.

Use CKKS homomorphic encryption for model updates only if the
implementation can be restored, integrated, and verified. Do not claim
encryption is working when it is unavailable or merely simulated.

After the IDS is implemented and validated, extend it into an SDN-based
Intrusion Prevention System (IPS). The IPS extension may send mitigation
requests to an SDN controller and apply OpenFlow rules in an isolated
test network.

IMPORTANT DISTINCTION

IDS detects malicious traffic and generates alerts. IPS detects
malicious traffic and takes prevention actions.

The research priority is the Federated IDS. IPS is a later extension.

============================================================ PHASE 9 —
IPS PREVENTION EXTENSION
============================================================

PROMPT TO SUBMIT AFTER APPROVING PHASE 8:

Perform Phase 9 only: extend the validated IDS into an SDN-based IPS in
the isolated test environment.

Prevention workflow: 1. Receive an IDS malicious-traffic prediction. 2.
Identify the corresponding switch and flow. 3. Apply configured
confidence/decision policy where supported. 4. Generate a mitigation
request. 5. Require manual approval by default. 6. Send an allowlisted
mitigation command to the SDN controller. 7. Apply a narrowly scoped
OpenFlow rule. 8. Record rule identifier, switch, flow, timestamp,
reason, and result. 9. Verify the flow behavior after applying the rule.
10. Support rule expiry/removal and safe rollback.

Provide three modes: - Detection only (default). - Manual approval
before blocking. - Automatic blocking (disabled by default and
restricted to isolated lab).

Safety: - Never block traffic on the user’s real network. - Do not
expose arbitrary controller commands through the web API. - Validate
switch and flow identifiers. - Use least-privilege controller access. -
Provide a clear emergency stop and rollback procedure. - Log every
mitigation attempt and result. - Distinguish requested, applied, failed,
and verified actions.

Test normal traffic, malicious test traffic, false positives, controller
failure, and rollback. Do not claim prevention success unless the flow
behavior is verified.

Create IPS_TEST_REPORT.md and update system documentation. STOP for
approval before Phase 10.

============================================================ FINAL
PROJECT ACCEPTANCE CRITERIA
============================================================

The project is not complete merely because the dashboard renders.

A feature is complete only when its backend behavior is implemented and
tested.

Minimum IDS acceptance: - Correct dataset validation and
preprocessing. - Actual GRU model integration. - Independent local
client training. - Actual federated aggregation. - Global model
distribution. - Predictions from the trained global model. -
Reproducible experiment records. - Honest evaluation metrics.

Privacy/security acceptance: - CKKS is real and verified, or clearly
reported unavailable. - Security mechanisms are individually tested. -
Limitations and threat assumptions are documented.

SDN/IPS acceptance: - Isolated SDN topology works. - Traffic-to-feature
mapping is tested. - IDS alerts identify the relevant flow. - IPS rules
are applied and verified in the lab. - Rollback works.

The project must always distinguish implemented, tested, simulated,
blocked, and not implemented functionality.
